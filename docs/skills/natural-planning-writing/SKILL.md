# 기획서 문체 다듬기

기획 의도와 근거를 유지하면서 팀이 직접 설명하는 한국어로 고친다. 탐지기 점수나 사람 작성 판정을 보장하지 않는다.

## 수정 범위

- 사용자가 지정한 문서나 구역만 읽고 수정한다. 문제 기획서를 요청했으면 PRD, 코드, 시나리오, DB 시드는 함께 바꾸지 않는다.
- 대상이 YAML이면 설명 문장만 수정하고 키, ID, 자료형, 들여쓰기와 참조 관계를 보존한다. Markdown의 표, 링크, 출처 번호도 유지한다.
- 기존 문체와 사용자가 제공한 글을 우선한다. 팀 기획서의 기본 어조는 짧고 담백한 서술형으로 한다. 채팅 말투를 문서에 그대로 옮기지는 않는다.

## 문장을 고르는 기준

- 추상적인 효과 대신 누가 언제 무엇을 하는지 적는다. 원문에 없는 행동이나 기능을 만들지는 않는다.
- 명사와 수식어가 이어지는 문장을 동사 중심으로 풀어 쓴다. 한 문장에 다른 주장이 섞이면 나눈다.
- 같은 주장을 요약, 통찰, 기대 효과에서 반복하면 정보가 가장 잘 이어지는 위치에 남긴다. 문제, 근거, 해법의 역할이 다른 문장까지 중복으로 지우지 않는다.
- 관용적인 강조나 문단 끝의 상투적인 결론은 실제 정보가 없으면 뺀다. 특정 단어, 문장부호, 표라는 이유만으로 일괄 삭제하지 않는다.
- 전문 용어는 독자와 목적에 맞게 남긴다. 평이한 단어로 바꾸면서 기술적 의미를 바꾸지 않는다.

## 보존할 것

- 수치, 단위, 조사 대상, 표본 수, 날짜, 인용문, 출처 링크와 출처 ID를 보존한다. 인용문을 다듬어 직접 인용으로 남기지 않는다.
- 관찰, 공개 질문, 가상 사례, 가정, 팀의 결정과 미확인을 구분한다. 가상 사례를 팀원의 실제 경험이나 인터뷰처럼 바꾸지 않는다.
- 가능성은 가능성으로 남긴다. 작은 표본이나 한 제품의 경고를 모든 사용자와 제품에 일반화하지 않는다.
- 의료 관련 문서는 '정보 없음'을 '안전함'으로, '상담 필요'를 '병용 금지'로 바꾸지 않는다. 복용 간격, 위험도, 효능 또는 권고를 문체 수정 중에 새로 만들지 않는다.
- 사실이나 설계의 충돌은 문장 수정과 구분해 짧게 알린다. 사용자가 범위 변경을 요청하지 않았다면 임의로 정책을 확정하지 않는다.

## 수정 예

- 원문: 사용자의 건강 관리 경험을 개선한다.
  - 앞 문맥에 해당 기능이 명시돼 있을 때: 먹는 약과 영양제를 등록하면 주의할 조합을 알려 준다.
- 원문: 영양제의 병용 안전성에 대한 정보 접근성이 부족하다.
  - 수정: 먹는 약과 영양제를 함께 확인할 정보를 찾기 어렵다.
- 원문: 칼슘을 사 드린 자녀는 부모님이 복용 중인 약물을 파악하지 못했다는 가상의 상황이다.
  - 수정: 가상 사례: 자녀가 부모님께 칼슘을 사 드렸지만, 부모님이 어떤 약을 드시는지는 몰랐다.

## 마무리

수정 전후를 대조해 주장과 근거의 연결, 인용, 수치, 가정 표시가 유지됐는지 확인한다. 구조화된 파일을 바꿨다면 기존 파서나 프로젝트 검사로 형식을 확인한다. 사용자가 설명을 원하지 않으면 수정한 문장만 보여 주고, 파일을 수정했다면 대상과 주요 변경을 짧게 알린다. 커밋이나 푸시는 사용자가 요청했을 때만 한다.
